# /test — 변경 범위 보호 테스트

현재 변경이나 지정된 이슈를 기준으로, 가장 작은 유효 테스트 세트를 추가하거나 검증 계획을 세워줘.

> **Tip:** 신규 기능 구현 시에는 `/tdd` (Red-Green-Refactor 워크플로) 를 먼저 고려. `/test` 는 기존 변경에 대한 회귀 테스트 범위 결정에 적합.

## Step 0: 프로젝트 설정 로드

Read `.claude/project.json` from the repo root. 존재하지 않으면 기본값 사용:
- `scripts.regression`: `null` (회귀 스크립트 없으면 테스트 프레임워크 자동 감지)

## 실행 순서

1. 현재 diff 또는 대상 이슈의 핵심 동작 확인
2. 회귀 위험이 가장 큰 분기부터 테스트 우선순위 지정
3. 프론트는 상태 분기와 핵심 렌더링, 백엔드는 계약/권한/집계, 데이터 작업은 재실행 가능성 중심으로 검토
4. 이미 있는 테스트 구조를 우선 활용하고, 없으면 최소한의 새 구조만 도입
5. `scripts.regression` 이 설정되어 있으면 해당 스크립트로 회귀 테스트 실행. 없으면 프로젝트 테스트 프레임워크를 자동 감지 (pytest, jest, vitest 등) 하여 실행.
6. 실행 가능한 테스트가 있으면 결과까지 확인하고, 없으면 필요한 이유를 설명

## 주의사항

- 변경과 무관한 대규모 테스트 인프라 작업으로 범위를 넓히지 말 것
- 핵심 사용자 플로우에 대한 무테스트 상태는 명확한 리스크로 보고할 것
